TOWER · BACKEND CONTRACT

Tower API Reference

What the Android client calls, screen by screen. Written against the running Spring Boot server so the client has a concrete contract instead of an assumption — and so the gaps are visible before they become surprises.

Base http://192.168.29.122:8080 Library E:/Entertainment Profile --spring.profiles.active=server

Correction to the brief

This is not a Jellyfin server

The build prompt says "Jellyfin-style REST assumed" and shows http://192.168.1.__:8096. That is the one line to change: this server speaks its own API on port 8080 under /api/media, shaped for these screens rather than bent to fit another product's schema. The brief already isolates transport in data/remote, so it is a one-file change on the client.

Everything below is real and tested. Where a screen needs something that does not exist yet, it says so rather than inventing an endpoint.

Every request

Three headers, and one other kind of token

Authorization: Bearer <jwt>
Everything except /api/health, /api/auth/register and /api/auth/login. Register returns 201 with a token; the account needs "role":"PARENT" to reach anything under /admin.
X-Profile-Id: <profileId>
Selects which family member is acting. Resume points, downloads, settings and unwatched marks are all per profile, not per account. Omit it and the account's first profile is used — convenient for curl, but the client should always send it. A profile id from another household returns 404, never someone else's data.
X-Admin-Key: <key>
Required by /api/media/admin/** and the library scan, in addition to a PARENT account. Both checks, because the key alone would let a child's device act as owner if it ever leaked into a shared client build. Failure is 403 either way, so the response cannot confirm a guessed key.
Authorization: Bearer <guest jwt>
Watch party guests. Carried the same way, but there is no account behind it: it reaches five endpoints for one film and everything else is 403 — including every call that takes X-Profile-Id, because a guest has no profile for one to name. The party, not the expiry, is what authorises it. See Watch together.

Two endpoints are public that look as though they should not be: POST /api/parties/{code}/guest and its polling twin. Someone asking to be let into a party has no credential yet — that is the whole reason they are asking.

Shapes you will meet everywhere

Errors and pages

Every failure is the same envelope, so the client needs one error path, not one per call: 

{ "timestamp": "2026-09-10T04:12:33Z",
  "status": 410,
  "error": "Gone",
  "message": "File is no longer on disk" }

Two status codes carry meaning worth handling separately. 410 means the row exists but the bytes do not — the drive is unplugged, not the title deleted, so say "disk offline" rather than "not found". 429 from a playback decision means every transcode slot is busy; the message names the limit.

Paged endpoints all return the same four fields alongside their items, and cap size at 100: 

{ "items": [ ... ], "page": 0, "size": 40,
  "totalItems": 214, "totalPages": 6 }

The central flow

Never guess whether a file will play

DIRECT PLAY versus WILL TRANSCODE is the brief's main motif, and the server decides it — not the client. Post the device's real codec support and use whichever URL comes back.

STEP 1 · ASK

The server probes the file if it never has, compares it against what the device declared, opens a playback session, and starts ffmpeg if a transcode is needed — so the playlist is already serving segments by the time you request it.

POST /api/media/items/{id}/playback-decision?startSeconds=76

MODE · DIRECT

Original bytes, byte-range served. Instant seeking, no server CPU. Keep the session parameter on the URL — it is what makes the stream visible in the admin panel and stoppable from it.

GET …/stream?session=<sessionId>

MODE · TRANSCODE

HLS, seeked to startSeconds. The stream itself starts at zero, so apply the offset client-side. Seeking past the transcoded region means asking for a new decision.

GET /api/media/transcode/{sessionId}/index.m3u8

reasons comes back as plain English on both paths — that is the sentence the playback plan card shows, and the debug view can print the whole list. /playback-decision/explain is the same logic with no session and no ffmpeg, and it works when the disk is offline, which is exactly when someone is asking why a title will not play. 

POST /api/media/items/{id}/playback-decision
{ "deviceName": "Arun's Pixel",
  "videoCodecs": ["h264", "hevc"], "audioCodecs": ["aac"],
  "containers": ["mp4", "mkv"], "maxHeight": 1080,
  "maxBitrate": 20000000, "supportsHls": true }

200 { "mediaItemId": "…", "mode": "DIRECT",
      "url": "/api/media/items/…/stream?session=9f3c…",
      "sessionId": "9f3c…", "startSeconds": 76,
      "mediaInfo": { "container": "mov,mp4,m4a", "videoCodec": "h264",
                     "width": 1920, "height": 1080, "bitrate": 8000000,
                     "durationSeconds": 8880.0, "probed": true },
      "reasons": ["Direct play: container and codecs match client capabilities"] }

A field left null in the request counts as unknown, and every unknown resolves toward transcoding. That is deliberate: wasting CPU is recoverable, a black screen is not.

Catalog

GET /api/media/items

410 when the file has gone from disk

GET /api/media/recently-added

A rail, not a list — capped at 50 and unpaged by design.

query types (comma-separated MediaType) · limit
→ ItemSummaryDto[]

GET /api/media/library-summary

Count, total bytes, per-category breakdown and the genre facet list.

→ { itemCount, totalBytes, categories[{ type, label, itemCount, totalBytes }], genres[] }

GET /api/media/home

The whole home screen in one call: the continue-watching row, the ranked rails and the library header, built from one consistent read of the library.

query types (comma-separated MediaType, default FILM,ANIME) · limit (per rail, capped at 50)
→ { continueWatching[], rails[{ key, title, rankedBy, items[{ item, score, reason }] }], library, weights{ rating, views, likes }, generatedAt }

Rails in render order — popular (the blend), top-rated, most-watched, most-liked, recently-added. An empty rail is omitted rather than sent as a bare heading, so a fresh library returns rails: []. score is 0–1 and present only on popular; reason is the subtitle naming why a title is there.

The blend normalises each signal to 0–1 and weights it 0.40 rating, 0.35 views, 0.25 likes. Rating leads because it is the only signal that exists before anyone has watched anything. Counts are normalised on a log curve against the library's own maximum, so one endlessly-rewatched favourite cannot flatten the rest of the rail into a rating sort. An unrated title is scored at the library mean, not zero, so footage the scraper never matched can still surface.

GET /api/media/home/popular

The blended rail alone, for a client that refreshes it on its own.

query types · limit
→ { key, title, rankedBy, items[{ item, score, reason }] }

PUT · DELETE · GET /api/media/items/{id}/like

The heart on a poster, per profile — each member of a household likes for themselves, while the count is the household's. Both write verbs are idempotent, so a retry on a flaky connection cannot double-count or toggle back. An item whose file is currently missing still accepts a like: the opinion is about the title, and an unplugged disk should not lose it.

→ { mediaItemId, liked, likeCount } · 404 when the item is unknown

POST /api/parties

→ 201 PartyDto { partyId, code, mediaItemId, itemTitle, live, maxMembers, youAreHost, members[], pending[], clock, capacityWarning }

Account holders, no approval — they can already stream any title, so gating the rendezvous would protect nothing. Safe to repeat on reconnect.

→ PartyDto · 409 every seat taken · 404 unknown code or ended party, deliberately indistinguishable

GET /api/parties/{code}/state

The polling fallback for a client that cannot hold a socket open. Same shape the socket pushes, just later.

→ PartyDto · 403 for a non-member

POST /api/parties/{code}/leave

The host leaving ends the party for everyone. No handover: the host's player is the clock.

→ 204

DELETE /api/parties/{code}

Host only. Everyone gets an ended frame before their socket closes, and guest streams stop at once.

→ 204

POST /api/parties/{code}/guest

Public. A friend with no account asks to be let in. What comes back is a place in a queue, not a credential — holding a code is weak evidence of an invitation.

body { name } — control characters stripped, capped at 40
→ { status: PENDING, requestId, pollToken, token: null }
429 rate limited per address, which is what makes guessing codes pointless

GET /api/parties/{code}/guest/{requestId}

Public. Poll for the host's answer. The pollToken is the secret — the requestId reaches the host in the accept prompt, so it is not one.

query token (the pollToken)
→ { status: PENDING | ADMITTED | DENIED, token?, expiresAt? }
unanswered requests expire after 5 minutes; the pollToken stays valid for the life of the party so a restarted app can fetch its token again

POST /api/parties/{code}/admit

The host's yes or no to one waiting guest.

body { requestId, allow }
→ PartyDto · 409 already answered, by a double tap or by the timeout

POST /api/media/guest/playback-decision

The guest's way in to playback. No item in the path — the title is in the token, put there when the host admitted them. Everything after this is the shared path.

query startSeconds
body ClientCapabilitiesRequest
→ PlaybackDecisionDto, identical to the account endpoint

WS /ws/party?code=…&token=…

The clock. The token is in the query because a browser cannot set a header on a WebSocket; a refused handshake is a 403 and never becomes a socket.

token an account JWT or a guest JWT
→ tick every 2s, and play/pause/seek the moment they happen

Watch together · the wire

Server frames. A pause carries exactly what a tick carries — the separate type exists so the client can say "Amma paused" instead of moving the bar silently. pending goes to the host alone, because it holds a name a stranger typed and nobody else can act on it. 

{"type":"tick",   "clock":{ … }, "by":null}
{"type":"play",   "clock":{ … }, "by":"Amma"}
{"type":"pause",  "clock":{ … }, "by":"Amma"}
{"type":"seek",   "clock":{ … }, "by":"Amma"}
{"type":"members","members":[{ id, name, role, host, joinedAt,
                               online, buffering, driftSeconds }]}
{"type":"pending","guest":{"requestId":"…","name":"Ravi","requestedAt":"…"}}
{"type":"ended",  "reason":"host ended it"}
{"type":"error",  "message":"only the host controls playback"}

clock = { state: PLAYING|PAUSED, positionSeconds,
          atEpochMillis, serverNowEpochMillis }

Client frames. The first three are host-only — a member sending one gets an error back and keeps its socket, because a stray control is a client bug worth surfacing rather than burying under a reconnect. report is for everyone: from the host it re-anchors the party to their real position, from anyone else it only records how far off they are. 

{"type":"play"|"pause"|"seek", "positionSeconds":812.4}
{"type":"report", "positionSeconds":812.1, "buffering":false}

Watch together · following the clock

The clock is an anchor, not a counter. positionSeconds was true at atEpochMillis and nothing advances it, so a slow tick, a missed tick and a reconnect mid-film all land on the same answer — where a counter incremented on a timer drifts by exactly as much as the timer did. Both timestamps are the server's, so a phone with a badly set clock cannot drag the party off. 

offset = serverNowEpochMillis - localNow      // re-estimate every frame
target = positionSeconds + (localNow + offset - atEpochMillis) / 1000
drift  = target - myPosition                 // only while state is PLAYING

drift > 2.0s        seek to target
0.35s – 2.0s        playbackRate 1.06 or 0.94 until under 0.1s, then 1.0
< 0.35s             do nothing

The rate nudge is the part that matters. A seek every few seconds is visible and ugly; a 6% rate change for two seconds is not.

Two behaviours to build the UI around. The host dropping pauses the party rather than ending it, so a tunnel or a locked phone does not end everyone's evening — and a party with nobody connected for fifteen minutes is closed.

Thumbnail scrubbing

Turning a timecode into a tile

The manifest gives the client everything it needs to crop a preview frame locally, which is what makes dragging the scrubber cost nothing. The six-frame filmstrip usually comes from a sheet already in memory. 

frame        = floor(seconds / intervalSeconds)
sheetIndex   = frame / framesPerSheet
indexInSheet = frame % framesPerSheet

First run

Getting from nothing to a playing film

1 · Account and profile

POST /api/auth/register with role: "PARENT", then POST /api/profiles for each family member. Keep the returned profile ids — every media call wants one.

2 · Index the disk

POST /api/media/library/scan with the admin key, then poll /api/media/library/status. First scan runs ffprobe per file, so it takes a while.

3 · Check the guesses

GET /api/media/admin/matches shows what the filename parser got wrong. On this library that was 24 titles — worth fixing before anyone browses.

4 · Confirm ffmpeg

Run ffprobe -version on the server first. Without it every title reports "not probed" and falls back to transcoding — and transcoding will not work either.
